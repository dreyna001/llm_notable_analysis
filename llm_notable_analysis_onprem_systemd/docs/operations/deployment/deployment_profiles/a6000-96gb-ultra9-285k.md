## Customer VM vLLM Settings

Install
[`vllm.rtx-pro-6000-blackwell-5analysts.drop-in.example`](../../../../deploy/systemd/vllm.rtx-pro-6000-blackwell-5analysts.drop-in.example)
over the generic packaged unit. These values match the stable running customer
VM and keep the backend context contract at 32K.

```ini
ExecStart=/opt/vllm/venv/bin/python -m vllm.entrypoints.openai.api_server \
    --model /opt/models/gemma-4-31B-it \
    --served-model-name gemma-4-31B-it \
    --host 127.0.0.1 \
    --port 8000 \
    --gpu-memory-utilization 0.85 \
    --max-model-len 32768 \
    --max-num-seqs 4 \
    --dtype bfloat16 \
    --distributed-executor-backend mp \
    --enforce-eager

Environment="CUDA_HOME=/usr/local/cuda-13.3"
Environment="PATH=/usr/local/cuda-13.3/bin:/opt/vllm/venv/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"
```

Notes:

- `32768` context is sufficient for notable JSON/text plus RAG/SPL prompt overhead.
- `CASE_QA_MODEL_CONTEXT_TOKENS=32768` must match in analyzer and portal env.
- Do not raise `--max-model-len` toward 128K unless a measured use case requires it.
- `--max-num-seqs 4` aligns with the measured vLLM bench `--max-concurrency 4` shape.
- `0.85`, `bfloat16`, and eager mode preserve the currently stable VM posture.
- The generic packaged unit remains a separate `0.92`/`dtype auto` starting point.
- The 285K CPU is not the inference bottleneck; vLLM/GPU throughput is.

## Analyzer `config.env` Recommended Settings

Copy these into `/etc/notable-analyzer/config.env` for this build. Values match
[`config.env.example`](../../../../config.env.example) defaults unless noted.
Merge secrets, Splunk/ServiceNow endpoints, and Postgres DSN locally; do not
commit live values.

### LLM (always)

```bash
LLM_API_URL=http://127.0.0.1:4000/v1/chat/completions
LLM_MODEL_NAME=gemma-4-31B-it
LLM_STRUCTURED_OUTPUT_MODE=prompt_json
LLM_MAX_TOKENS=4096
LLM_TIMEOUT=240
CASE_QA_MODEL_CONTEXT_TOKENS=32768
```

Use `LLM_TIMEOUT=120` only for `CAPABILITY_PROFILES=core` with no SPL interpretation.

### Concurrency (start conservative)

```bash
CONCURRENCY_ENABLED=false
MAX_WORKERS=1
MAX_QUEUE_DEPTH=8
```

After load test on this host:

```bash
CONCURRENCY_ENABLED=true
MAX_WORKERS=2
MAX_QUEUE_DEPTH=16
```

The current customer baseline remains sequential. Do not apply the raised
values merely because vLLM permits four active sequences; that capacity also
serves portal chat.

Confirm Splunk search concurrency with the Splunk platform owner before running

### RAG (when `rag` is enabled)

Keep Postgres backend defaults. Stage Mixedbread models before enabling RAG:

```bash
RAG_BACKEND=postgres
RAG_EMBEDDING_MODEL=mixedbread-ai/mxbai-embed-large-v1
RAG_VECTOR_DIMENSIONS=1024
RAG_FAIL_CLOSED=false
RAG_RERANK_ENABLED=false
```

The 285K has headroom for optional rerank after the reranker model is staged.

Optional quality bump after staging the default reranker model
(`RAG_RERANK_MODEL=mixedbread-ai/mxbai-rerank-large-v2` in the template):

```bash
RAG_RERANK_ENABLED=true
```

`gemma-4-31B-it` maps to the repo's **120B-class** RAG snippet/budget defaults
(`RAG_MAX_SNIPPETS_120B=5`, `RAG_CONTEXT_BUDGET_CHARS_120B=2200`) automatically.

## Expected Throughput (Rough)

Measured direct-vLLM baseline (2048 input / 512 output tokens, `--max-concurrency 4`,
no LiteLLM, no analyzer):

- [`a6000-96gb-ultra9-285k-vllm-benchmark-2026-05-28.md`](a6000-96gb-ultra9-285k-vllm-benchmark-2026-05-28.md)
- ~590 single-call equivalents/hour at that serving shape; do not convert directly to
  notables/hour.

Sequential analyzer baseline (`CONCURRENCY_ENABLED=false`, `MAX_WORKERS=1`):

| Profile | Order of magnitude |
|---------|-------------------|
| `core` only | ~20-50 notables/hour |
| `core,rag,spl_readonly` + `QUERY_RESULT_INTERPRETATION_ENABLED=true` | ~4-12 notables/hour |

`QUERY_RESULT_INTERPRETATION_ENABLED` defaults to `false` in the template; enable it
only when the third LLM interpretation call is in scope.

Actual latency depends on alert size, RAG hit rate, Splunk response time, and vLLM
batching. Measure before raising concurrency.

## Validation

```bash
curl -sS http://127.0.0.1:8000/v1/models
curl -sS http://127.0.0.1:4000/v1/models
cd /path/to/llm_notable_analysis_onprem_systemd
sudo bash scripts/smoke_service_chain.sh --config-env /etc/notable-analyzer/config.env
```

Before enabling `CONCURRENCY_ENABLED=true`, raising `MAX_WORKERS`, or raising
`--max-num-seqs` above `4`, run an
inference serving benchmark:

- [`LLM_INFERENCE_BENCHMARKING.md`](../../llm/LLM_INFERENCE_BENCHMARKING.md)

Process representative JSON and text notables. Review:

- parse/repair metadata in reports
- LLM latency and timeout behavior
- GPU memory via `nvidia-smi` during peak load

## Change Only After Load Test

- `CONCURRENCY_ENABLED=true`
- `MAX_WORKERS=2` or higher
- `--max-num-seqs` above `4`
- `--gpu-memory-utilization` above `0.85`
- removal of `--enforce-eager`
- `RAG_RERANK_ENABLED=true`
- Higher Splunk concurrency combined with multi-notable workers

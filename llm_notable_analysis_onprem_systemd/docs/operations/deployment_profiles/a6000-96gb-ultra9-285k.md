# Deployment Profile: `a6000-96gb-ultra9-285k`

## Status

Active baseline for the current on-prem build.

## Hardware

| Component | Value |
|-----------|-------|
| GPU | 1x NVIDIA RTX PRO 6000 (96 GB VRAM) |
| CPU | Intel Core Ultra 9 Processor 285K (24 cores / 24 threads) |
| Default model | `gemma-4-31B-it` |
| Inference stack | vLLM (`127.0.0.1:8000`) -> LiteLLM (`127.0.0.1:4000`) -> analyzer |

## Recommended Capability Profiles

Start narrow, add profiles after validation:

```bash
# Baseline production
CAPABILITY_PROFILES=core

# After KB and Splunk owners approve integrations
CAPABILITY_PROFILES=core,html_reports,rag,spl_readonly
```

## vLLM Recommended Settings

Use the packaged single-GPU unit in `deploy/systemd/vllm.service` unless the host
paths differ.

```ini
Environment="CUDA_VISIBLE_DEVICES=0"

ExecStart=/opt/vllm/venv/bin/python -m vllm.entrypoints.openai.api_server \
    --model /opt/models/gemma-4-31B-it \
    --served-model-name gemma-4-31B-it \
    --host 127.0.0.1 \
    --port 8000 \
    --gpu-memory-utilization 0.92 \
    --max-model-len 32768 \
    --dtype auto \
    --distributed-executor-backend mp
```

Optional after load-testing `CONCURRENCY_ENABLED=true` and `MAX_WORKERS=2`:

```ini
    --max-num-seqs 4 \
```

Notes:

- `32768` context is sufficient for notable JSON/text plus RAG/SPL prompt overhead.
- Do not raise `--max-model-len` toward 128K unless a measured use case requires it.
- The 285K CPU is not the inference bottleneck; vLLM/GPU throughput is.

## Analyzer `config.env` Recommended Settings

Copy these into `/etc/notable-analyzer/config.env` for this build. Merge secrets,
Splunk/ServiceNow endpoints, and Postgres DSN locally; do not commit live values.

### LLM (always)

```bash
LLM_API_URL=http://127.0.0.1:4000/v1/chat/completions
LLM_MODEL_NAME=gemma-4-31B-it
LLM_STRUCTURED_OUTPUT_MODE=prompt_json
LLM_MAX_TOKENS=4096
LLM_TIMEOUT=240
```

Use `LLM_TIMEOUT=120` only for `CAPABILITY_PROFILES=core` with no SPL interpretation.

### Concurrency (start conservative)

```bash
CONCURRENCY_ENABLED=false
MAX_WORKERS=1
MAX_QUEUE_DEPTH=8
```

After load test on this host:

```bash
CONCURRENCY_ENABLED=true
MAX_WORKERS=2
MAX_QUEUE_DEPTH=16
```

### Splunk investigation (when `spl_readonly` is enabled)

```bash
INVESTIGATION_MAX_QUERIES_PER_ALERT=6
INVESTIGATION_MAX_CONCURRENT_QUERIES=6
SPLUNK_SEARCH_TIMEOUT_SECONDS=30
```

Confirm Splunk search concurrency with the Splunk platform owner before running
all six queries in parallel across multiple notables.

### RAG (when `rag` is enabled)

Keep Postgres backend defaults. The 285K has headroom for optional rerank after
the reranker model is staged:

```bash
RAG_BACKEND=postgres
RAG_FAIL_CLOSED=false
RAG_RERANK_ENABLED=false
```

Optional quality bump after staging `BAAI/bge-reranker-base`:

```bash
RAG_RERANK_ENABLED=true
```

`gemma-4-31B-it` uses the repo's **120B-class** RAG snippet/budget defaults automatically.

## Expected Throughput (Rough)

Sequential baseline (`CONCURRENCY_ENABLED=false`, `MAX_WORKERS=1`):

| Profile | Order of magnitude |
|---------|-------------------|
| `core` only | ~20-50 notables/hour |
| `core,rag,spl_readonly` + interpretation | ~4-12 notables/hour |

Actual latency depends on alert size, RAG hit rate, Splunk response time, and vLLM
batching. Measure before raising concurrency.

## Validation

```bash
curl -sS http://127.0.0.1:8000/v1/models
curl -sS http://127.0.0.1:4000/v1/models
sudo bash scripts/smoke_service_chain.sh --config-env /etc/notable-analyzer/config.env
```

Process representative JSON and text notables. Review:

- parse/repair metadata in reports
- LLM latency and timeout behavior
- GPU memory via `nvidia-smi` during peak load

## Change Only After Load Test

- `CONCURRENCY_ENABLED=true`
- `MAX_WORKERS=2` or higher
- `--max-num-seqs`
- `RAG_RERANK_ENABLED=true`
- Higher Splunk concurrency combined with multi-notable workers
